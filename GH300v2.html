GH-300: GitHub Copilot Fundamentals

Learn the concepts, then immediately connect them to a real developer workflow.

This handbook is deliberately split into Learning and Hands-on Lab. The Learning area explains the ideas. The Lab turns those ideas into one connected project that learners build, test, document, review and publish.

How to Use This Handbook

Do not simply copy every prompt from this handbook. A prompt is useful only when it is connected to the right context, the right developer task and a verification step.

The intended learning loop is:

Learn→Open IDE→Apply→Inspect→Test→Improve→Document→Review

Responsible AI

The first question is not “Can Copilot generate this?” It is “Should we use this output, and how will we verify it?”

Fairness

Could the solution disadvantage people or groups?

Inclusiveness

Does it work for different users and circumstances?

Reliability & Safety

What happens when the AI is wrong?

Privacy & Security

What information is being provided and what risks can the generated code introduce?

Transparency

Can people understand the system and its limitations?

Accountability

Who reviews and owns the final decision or code?

Prompt Engineering

R-C-C-O pattern

Role+Context+Constraints+Output

Good prompts make the task explicit. Great prompts also tell Copilot what it must preserve, what it must not do, and how you want the result presented.

Weak

Fix this code.

Controlled

Review the selected function.

Find the root cause.
Do not change the public method signature.
Explain the issue first.
Then propose the smallest safe fix.
Return the proposed change as a diff.

Advanced Features

CapabilityUse it when...
Ghost textYou are actively typing and want fast code completion.
ChatYou need explanation, planning, debugging or broader reasoning.
Inline ChatYou want a focused change without leaving the current code.
Slash commandsYou have a common developer intention such as explain, test or fix.
AgentsThe task involves multiple steps and project context.
Workspace/context referencesThe answer needs knowledge from your actual project.

IDE, Chat, GitHub.com and CLI

IDE→Chat→GitHub.com→CLI→PR

The important connection is not memorizing interfaces. It is understanding which surface is closest to the task.

  • IDE: write and modify code.
  • Chat: discuss and reason.
  • GitHub.com: collaborate around repository work, issues and PRs.
  • CLI: work with commands, scripts and terminal workflows.
  • PR: review and collaborate before integration.

Management & Customization

When Copilot moves into an organization, governance becomes part of the developer experience. Think about plans, access, policies, privacy, content exclusions, public-code matching and troubleshooting.

Copilot Across the SDLC

Requirement→Plan→Build→Test→Debug→Document→Review→PR→Maintain

This is the connection that the hands-on lab makes visible. We will use one project and repeatedly apply different Copilot capabilities to it.

Tokens, Context and Usage

Think of context as the information Copilot has available for the current task. More context is not automatically better. The goal is relevant context.

Too broad:
Read everything and rewrite the application.
Focused:
Review the selected validator.
Find up to 5 issues.
Do not modify code.
Return severity + recommendation.

Hands-on Lab — Build a Real Project with GitHub Copilot

Important: this is not a prompt-copying exercise.

You will build one small application from beginning to end. Every time you learn a GH-300 concept, you will immediately use that concept on the same project.

Learn→Connect→Do→Verify→Reflect

Trainer instruction

Open the IDE with the learners. Keep this page in the browser. Switch between the Learning tab when explaining a concept and the Hands-on Lab tab when it is time to build.

Step 0 — Open the Development Environment

Choose one environment

  • Visual Studio Code + GitHub Copilot, or
  • Visual Studio + GitHub Copilot where supported by the learner's setup.

Sign in to GitHub, verify Copilot access and create a new repository named:

daily-kpi-note
Learning connection:
Module 2 — Introduction to GitHub Copilot: setup, suggestions and interaction modes.
What you do now:
Open the IDE, create the repository/project and verify that Copilot suggestions appear.

First prompt — do not build yet

I am starting a small project called Daily KPI Note.

Before writing any code, tell me:
1. what information you need from me;
2. what assumptions you would make;
3. what the smallest useful version of this application should contain.

Do not create files yet.

Step 1 — Turn a Business Requirement into a Technical Plan

Connects to:
Module 3 — Prompt Engineering + Module 7 — Developer Use Cases.
Why now?
We are using prompting for planning, not code generation.
I want to build a tiny web application called Daily KPI Note.

A user should be able to:
- enter KPI name;
- enter numeric value;
- choose a category;
- save it;
- see saved KPIs;
- delete a KPI;
- see count and total.

Audience:
analytics professionals and business users.

Constraints:
- keep the first version simple;
- no authentication;
- no database initially;
- avoid unnecessary libraries.

Do not write implementation code yet.

Return:
1. architecture;
2. minimum file structure;
3. data shape;
4. API routes;
5. validation rules;
6. implementation order;
7. testing strategy.
Checkpoint: Do not continue until the learner can explain the architecture in their own words.

Step 2 — Build the Minimum Viable Application

Connects to:
Module 2 — Copilot + Module 4 — Advanced Features.
Capability:
Agent / Chat / Inline Chat depending on the learner's available Copilot experience.
Using the approved Daily KPI Note plan, implement the smallest working version.

Requirements:
- one simple page;
- KPI name, category and numeric value;
- add KPI;
- list KPIs;
- delete KPI;
- show count and total;
- in-memory storage;
- basic validation;
- minimal UI.

Do not add:
- authentication;
- database;
- frontend framework;
- unnecessary abstractions.

After implementation:
1. summarize the files created;
2. explain the data flow;
3. list assumptions;
4. list what I must manually verify.

Do not claim the application is tested yet.

Human checkpoint

  • Open every generated file.
  • Understand the API route(s).
  • Run the application.
  • Add one KPI.
  • Add a second KPI.
  • Delete one KPI.
  • Confirm count and total.
  • Check an invalid input.

Step 3 — Use Context Instead of Re-explaining Everything

Connects to:
Module 4 — Advanced Features + Module 5 — Across Environments.
Goal:
Show why project context makes Copilot more useful than a generic chatbot.
Where is the code responsible for calculating the KPI total?

Use the current project context.

Tell me:
1. file name;
2. function or method;
3. where it is called;
4. what input it receives;
5. one edge case I should test.

Do not modify anything.

Then move to Inline Chat

Improve only this validation.

Rules:
- KPI name cannot be empty;
- category cannot be empty;
- value must be numeric;
- negative values are rejected.

Keep the existing structure.
Show the proposed change before applying it.
Teaching point: The same natural-language skill is now being used at a different Copilot surface. The learner should be able to explain why Chat and Inline Chat are different choices.

Step 4 — Testing: Make Copilot Prove Its Work

Connects to:
Module 8 — Develop Unit Tests Using GitHub Copilot Tools.
Goal:
Move from “Copilot generated code” to “the code has evidence.”

First ask for test cases

For the KPI validation and total-calculation logic,
identify the most important unit-test cases.

Include:
- normal input;
- empty input;
- zero;
- negative value;
- invalid numeric input;
- multiple KPI values.

Return:
case + input + expected result + reason.

Do not write tests yet.

Then generate tests

Now create unit tests for the cases we identified.

Requirements:
- keep tests readable;
- one behaviour per test;
- use descriptive test names;
- do not change production code;
- create only the necessary test code.

Deliberately create a failure

Change one validation rule or calculation operator manually. Run the tests.

The test suite is failing.

Do not change code yet.

Explain:
1. expected result;
2. actual result;
3. likely root cause;
4. smallest safe fix;
5. regression risk.

Fix and verify

Apply the smallest safe fix for the identified root cause.

Do not make unrelated changes.

After the fix:
1. show the changed code;
2. explain why it fixes the failure;
3. run the relevant tests;
4. report the test result.

Step 5 — Documentation Is Another Copilot Use Case

Connects to:
Module 4 — Advanced Features + Module 7 — Developer Use Cases.
Goal:
Update documentation from the actual implementation rather than asking AI to invent a README.
Review the current Daily KPI Note project and update README.md.

Document only what currently exists.

Include:
- purpose;
- features;
- architecture;
- setup;
- run instructions;
- API routes;
- validation;
- testing;
- known limitations.

If the current README conflicts with the code,
identify the conflict before changing it.

Do not invent functionality.

Open README.md and compare it with the actual application. Ask the learner: “Can you prove every important statement in this README from the code?”

Step 6 — Code Review Before Collaboration

Connects to:
Module 1 — Responsible AI + Module 7 — Developer Use Cases.
Goal:
Use AI to assist review while keeping the human responsible for the final decision.
Review the current Daily KPI Note changes as a senior developer.

Report only:
- correctness issues;
- validation issues;
- obvious security risks;
- missing important tests;
- unnecessary complexity;
- documentation mismatches.

For each finding provide:
- severity;
- file/location;
- why it matters;
- recommendation.

Do not modify anything.

Responsible-AI checkpoint

For every Copilot finding, ask:

  1. Is the finding actually correct?
  2. Can I verify it from the code?
  3. Is it important enough to act on?
  4. Could Copilot itself have misunderstood the context?

Step 7 — Git, Pull Request and Collaboration

Connects to:
Module 5 — Environments + Module 10 — Enterprise concepts.
Goal:
Move from local development into collaborative development.

Commit message

Suggest a concise git commit message for the current changes.

Explain why it accurately represents the change.
Do not commit anything.

PR description

Using the current git diff, prepare a concise pull request description.

Include:
- business purpose;
- files changed;
- behaviour changed;
- tests run;
- known limitations;
- review risks.

Use only information present in the current changes.
Do not invent evidence.

On GitHub

  1. Push the branch.
  2. Open the pull request.
  3. Review the generated summary.
  4. Open the changed files.
  5. Use Copilot to explain important diffs.
  6. Review CI/test evidence.
  7. Make the final human decision.

Step 8 — Change the Requirement Mid-Project

Connects to:
Prompt Engineering + Agents + Testing + Documentation + SDLC.
New requirement:
Add a “Clear All KPIs” feature without breaking existing functionality.
Add a “Clear All KPIs” feature.

Constraints:
- keep the existing UI style;
- ask for confirmation before deletion;
- keep current API behaviour unless necessary;
- add unit tests;
- update README;
- do not break existing functionality.

Before changing code:
1. identify affected files;
2. propose the smallest implementation plan;
3. identify tests that need to be added or updated.

Do not implement yet.

Now let Copilot implement the approved plan

Implement only the approved Clear All KPIs plan.

After implementation:
- summarize changed files;
- explain the data flow;
- identify tests to run;
- identify documentation changes;
- do not claim success until verification is complete.

Repeat the lifecycle

Implement→Test→Fix→Document→Review→PR

This repetition is intentional. It demonstrates that Copilot skills are reusable rather than one-off prompts.

Step 9 — Optional Persistence Upgrade

Connects to:
Planning, context, architecture, testing and documentation.
Upgrade:
Move from in-memory storage to PostgreSQL.
The application currently stores KPIs in memory.

I have PostgreSQL running locally.

Do not change code yet.

Identify:
1. where persistence currently happens;
2. the smallest PostgreSQL change;
3. proposed table schema;
4. required environment variables;
5. tests that must change;
6. security considerations for connection strings.

Keep the existing UI and API routes unchanged.

Return a short implementation plan only.

After implementation, prove persistence by:

  1. creating a KPI;
  2. stopping the application;
  3. starting it again;
  4. confirming the KPI still exists;
  5. running the complete test suite.

Identify where this behaviour is implemented,

Prompt Library — Testing

Identify the most important unit-test cases for this behaviour.

Do not write tests yet.

Prompt Library — Fixing

The test is failing.

Do not change code yet.
Explain expected result, actual result, likely root cause,
smallest safe fix and regression risk.

Prompt Library — Documentation

Update the README using the current project as the source of truth.
Do not invent features.
If documentation conflicts with code, identify the conflict first.

Prompt Library — Review

Review the current changes as a senior developer.

Report correctness, validation, security, missing tests,
complexity and documentation issues.

For every finding include severity, location,
why it matters and recommendation.

Do not modify anything.

Prompt Library — Pull Request

Using the current diff, prepare a concise PR description.

Include business purpose, files changed, behaviour,
tests run, limitations and risks.

Use only evidence present in the changes.
