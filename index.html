GH-300: GitHub Copilot Fundamentals

A practical developer handbook for understanding Copilot, using it effectively, and applying it throughout the software development lifecycle.

Learn the idea → see the analogy → paste the prompt → inspect the result → test it → improve it → document it → review it.

This handbook is designed to work for learners learning reference.

Welcome

GitHub Copilot becomes much easier to understand when you stop thinking of it as a single “code generator”. It is better understood as an AI pair programmer that can participate in many different activities: understanding a repository, writing code, explaining code, generating tests, fixing failures, documenting changes, helping with terminal commands, reviewing pull requests and supporting developers across the SDLC.

The purpose of this handbook is therefore not to memorize buttons. It is to understand which Copilot capability to use for which developer problem.

The core mental model

Ask→Plan→Build→Test→Fix→Document→Review→Ship

Copilot accelerates the work. The developer remains responsible for deciding what should be built and verifying what was produced.

2. Responsible AI with GitHub Copilot

Responsible AI is the foundation of the course. Before asking “Can Copilot do this?”, a developer should also ask “Should we do this, and how do we verify the result?”

Fairness

Could the output systematically disadvantage a person or group?

Inclusiveness

Does the solution work for different users, abilities and circumstances?

Reliability & Safety

What happens when the model is wrong?

Privacy & Security

What information is being provided, and could the generated solution introduce vulnerabilities?

Transparency

Can people understand what the system is doing and why?

Accountability

Who reviews and owns the final decision or code?

Analogy: Copilot is like a brilliant junior developer. You appreciate the speed, but you still review their pull request.

Mini demonstration

Evaluate this hypothetical employee-ranking approach.

Rank employees using only short natural-language descriptions.
Then identify:
1. what information may be missing;
2. where bias could enter;
3. why the ranking may be unreliable;
4. what a human reviewer should verify.

Do not produce a final hiring decision.

3. Introduction to GitHub Copilot

What is Copilot?

GitHub Copilot is an AI-powered coding assistant that can help developers generate, understand, refactor and debug code through inline suggestions and conversational interaction.

Analogy: Predictive text for developers — except the “next word” can become a complete function, test, explanation or implementation idea.

Ghost text

Start typing or describe intent in a comment. Copilot proposes code. Tab accepts; ignore or undo when it is not right.

Chat

Move from completion to conversation: explain, design, debug, compare, refactor or plan.

First live demo

# Create a function that accepts a list of sales values
# and returns the total, average, minimum and maximum.

Pause. Let Copilot suggest the implementation. Accept it, then explain that the grey suggestion is a proposal—not automatically trustworthy code.

4. Prompt Engineering — How Developers Talk to Copilot

A good prompt is not necessarily long. It is clear, relevant, constrained and grounded in the task.

The R-C-C-O pattern

Role / Perspective+Context+Constraints+Output
ElementQuestionExample
RoleWho should Copilot think like?“Act as a senior C# reviewer.”
ContextWhat does it need to know?“Review the selected service and its unit tests.”
ConstraintsWhat must it not/change?“Do not change the public API.”
OutputWhat should come back?“Return 5 findings with severity and recommendation.”

Weak

Fix this code.

Better

Review the selected function.

Find the root cause of the failing validation.
Do not change the public method signature.
Explain the issue first.
Then propose the smallest safe fix.
Return the proposed change as a diff.

Prompt optimization principles

  • Give Copilot the right context, not all available context.
  • State what should not change.
  • Ask for a plan before a large implementation.
  • Bound the output when you need a concise answer.
  • Ask Copilot to distinguish facts, assumptions and recommendations.
  • Use follow-up prompts instead of restarting from zero.
  • For sensitive or high-impact work, explicitly ask for risks and verification steps.

5. Advanced GitHub Copilot Features

This is where Copilot starts feeling like a development partner rather than autocomplete.

FeatureWhat it solvesAnalogy
ChatComplex questions and multi-step reasoning.Turn your chair and ask your teammate.
Inline ChatFocused changes without leaving the code.Point at one paragraph and say “change this.”
Slash commandsCommon developer tasks with compact commands.Keyboard shortcuts for standard jobs.
AgentsProject-aware tasks that require context and multiple actions.“Take this task and use the tools you need.”
Context referencesGround the answer in a workspace, file or other relevant source.Give your teammate the exact document.
Ghost textFast completion while typing.Predictive text for code.

Slash command discovery

Open Chat and type only:

/

Let the current menu show what your environment supports. Use the available command rather than memorizing a command that may have changed.

/explain

Use it when you need to understand selected or active code.

/tests

Use it when you need unit tests for selected code.

/fix

Use it after identifying a bug or failure.

/docs

Use it where your Copilot client exposes documentation assistance.

/compact

Use the current compact/summarize capability when exposed after a long conversation.

@workspace

Ask project-level questions using workspace context where supported.

The powerful combination

Inline Chat + slash command + context

Select the validation function → Inline Chat → /tests

This is the kind of quick trick developers should remember: individual features become much more useful when combined.

6. Copilot Across Environments

IDE→Chat→GitHub.com→CLI→PR

IDE

Best when you are actively writing or editing code. Use completion, Inline Chat, context and file-level assistance.

GitHub.com

Useful around repositories, issues, pull requests and collaborative review workflows.

CLI

Useful when the work itself lives in the terminal: commands, scripts, diagnostics and automation.

PR workflow

Useful when code is moving from “my branch” to “team-reviewed change”.

CLI safety demo

Explain the command I need to run to execute this project's tests.

Do not execute anything.
Explain:
1. what the command does;
2. what files it may read/change;
3. what a successful result looks like.

Rule: AI can suggest a command. The developer should understand the command before executing it.

7. Management, Plans, Privacy & Customization

Copilot is not only a developer tool; in organizations it becomes a governed service. The important question changes from “Can I use Copilot?” to “How should our organization use Copilot safely and consistently?”

AreaWhat to understand
PlansIndividual and organizational offerings provide different capabilities and management controls.
Policy managementOrganizations can control access and selected Copilot capabilities.
Content exclusionsSome files or directories may need to be excluded from Copilot analysis according to organizational policy.
Public-code matchingOrganizations can configure relevant controls around suggestions that match publicly available code.
Privacy & data handlingUnderstand the applicable product, plan, settings and organizational policies before using sensitive information.
TroubleshootingSign-in, extension, network, licensing, policy and environment configuration can all affect Copilot behaviour.
Analogy: Content exclusion is like telling your assistant, “You can work in this office, but this locked room is out of bounds.”

9. Complete Hands-on Demo — Daily KPI Note

The running project

We use one intentionally small application so every GH-300 capability can be demonstrated without spending the entire session on application development.

daily-kpi-note/
├── app.py
├── index.html
├── style.css
├── app.js
├── test_app.py
└── README.md

The app lets a user add a KPI name, category and numeric value, list entries, delete entries, and see count and total.

Step 1 — Ask before building

I want to build a tiny web app called Daily KPI Note.

A user should be able to:
- enter KPI name;
- enter numeric value;
- choose a category;
- save it;
- see saved KPIs;
- delete a KPI;
- see count and total.

Audience: analytics professionals and business users.

Do not write code.
Explain the smallest architecture, minimum files,
and three important validation rules.

Trainer explanation: We are using Copilot as a thinking partner before using it as an implementation partner.

Step 2 — Plan the implementation

Create a minimal implementation plan for Daily KPI Note.

Use Python + Flask, HTML/CSS/vanilla JavaScript,
and an in-memory Python list initially.

Constraints:
- no authentication;
- no database yet;
- no frontend framework;
- no unnecessary abstractions.

Return:
1. file structure;
2. data shape;
3. API routes;
4. implementation sequence;
5. test strategy.

Do not create files yet.

Step 3 — Build with Agent mode

Implement the approved Daily KPI Note plan.

Create the required files yourself.

Requirements:
- one simple page;
- KPI name, category and numeric value;
- add/list/delete KPI;
- count and total;
- in-memory storage;
- simple validation;
- minimal UI;
- no authentication;
- no unnecessary libraries.

After implementation:
1. summarize files;
2. explain browser-to-API data flow;
3. identify what I should review;
4. do not claim it is tested until tests run.

Inspect the generated files and changes before accepting them.

Step 4 — Show ghost text

# Calculate the total KPI value

Pause and let the suggestion appear. Accept it, undo it, change the comment and observe how the suggestion changes.

Step 5 — Explain existing code

/explain

If the current UI does not expose the command, use:

Explain the selected code in simple language.
Tell me its inputs, outputs and important edge cases.

Step 6 — Ask a project question using context

Where is the code that calculates the KPI total?

Explain:
1. which file contains it;
2. which function is responsible;
3. where it is called from.

Repeat with the workspace/file context available in your client and compare the quality of the response.

Step 7 — Inline Chat for a focused edit

Improve only this validation.

Rules:
- KPI name cannot be empty;
- category cannot be empty;
- value must be numeric;
- negative values are rejected.

Keep the existing structure.
Show the proposed change before I accept it.

Show the diff. Accept or reject deliberately.

Step 8 — Generate tests

/tests ensure the function rejects empty KPI names,
rejects negative values, accepts zero,
and calculates totals correctly

Run the tests. Do not merely show generated test code—show the test runner.

Step 9 — Deliberately break the code

Change one operator in the calculation or remove a validation condition. Run the tests and show the failure.

The test is failing.

Do not modify anything yet.

Explain:
1. expected result;
2. actual result;
3. likely root cause;
4. smallest safe fix;
5. regression risk.

Then use /fix or a focused fix prompt. Apply the change and rerun the tests.

Step 10 — Update documentation

Update README.md to accurately describe the current application.

Include:
- purpose;
- features;
- setup/run;
- API routes;
- validation;
- test command;
- current in-memory limitation.

Use the actual project as the source of truth.
Do not invent features.

Now add one feature—such as “Clear All KPIs”—and update the README again. This demonstrates that documentation is part of the lifecycle.

Step 11 — Review the change

Review the current Daily KPI Note changes as a senior developer.

Report only:
- correctness issues;
- validation issues;
- obvious security risks;
- missing important tests;
- unnecessary complexity;
- documentation mismatches.

For each finding give:
- severity;
- file/location;
- why it matters;
- recommendation.

Do not modify anything.

Step 12 — Git commit

Suggest a concise git commit message for the current changes.
Explain why it accurately represents the change.
Do not commit anything.

Review the diff, then commit yourself or approve the command after understanding it.

Step 13 — Pull Request

Using the current git diff, prepare a concise PR description.

Include:
- business purpose;
- files changed;
- behaviour changed;
- tests run;
- known limitations;
- review risks.

Use only information present in the current changes.
Do not invent evidence.

Open the PR on GitHub and use Copilot to summarize the PR and explain important diffs.

Step 14 — Optional PR automation

If your current Copilot CLI/repository exposes these workflows, explore:

/pr create
/pr fix feedback
/pr fix ci
/pr fix

Explain /pr auto as a higher-autonomy workflow rather than using it casually in a live training session.

Step 15 — PostgreSQL architecture upgrade

The application currently stores KPIs in memory.

I have PostgreSQL running locally.

Do not change code yet.

Identify:
1. where persistence currently happens;
2. the smallest PostgreSQL change;
3. the table schema;
4. required environment variables;
5. tests that must change.

Keep the UI and API routes unchanged.
Return a short implementation plan only.

After approving the plan, implement it and prove that a KPI survives an application restart.

10. Testing with GitHub Copilot

Testing is where Copilot moves from “looks good” to “let's verify it.”

Generate→Run→Fail→Diagnose→Fix→Rerun

Happy path

Does normal input work?

Boundary

What happens at zero, maximum, minimum and empty values?

Invalid input

What should be rejected?

Regression

Does the fix break something that previously worked?

Ask Copilot for edge cases

For this function, identify important edge cases
that a unit test suite should cover.

Return:
- case;
- input;
- expected result;
- why it matters.

Do not write tests yet.

11. Tokens, Context & Usage Optimization

What is a token?

A token is a small unit of text processed by a language model. Words, punctuation and pieces of words can be represented as tokens.

Analogy: Imagine a conversation made from Lego pieces. The more pieces you send and the more pieces the model generates, the more model processing is involved.

Prompt+Context+Conversation+Model output→Usage
TechniqueWhy it helpsExample
Use focused contextReduces irrelevant information.Reference one file/function.
Use slash commandsPackages common intentions into concise interactions./tests instead of a long testing instruction.
Bound the outputPrevents unnecessarily large answers.“Return 5 findings maximum.”
Plan firstAvoids giant speculative implementations.“Plan only. Do not edit.”
Work incrementallySmaller changes are easier to validate.Feature → test → verify.
Use the appropriate modelMatch model capability to task complexity.Simple explanation vs complex architecture.
Compact long conversations when availableReduces accumulated noise.Use the current compact/summarize feature exposed by the client.

Token-heavy

Read the whole repository,
all documentation,
all previous messages,
all tests,
all configuration,
and then rewrite everything.

Token-conscious

Review the selected validator.

Find up to 5 correctness issues.
Do not modify code.
Return severity + recommendation.

Current Copilot usage and billing can depend on model and token consumption, and GitHub's billing model has evolved over time. Always check the current plan documentation before teaching numerical limits as permanent rules.

12. Documentation Is Part of Development

A common developer mistake is treating documentation as a final ceremony. With Copilot, documentation can be updated as the code changes.

Implement→Test→Document→Review→PR

README maintenance prompt

Review the current repository and update README.md.

Document only features that currently exist.
Include:
- purpose;
- architecture overview;
- setup;
- run instructions;
- API routes;
- validation;
- testing;
- known limitations.

If the code and README disagree,
identify the disagreement before changing the documentation.

13. Pull Requests, Code Review & Collaboration

The PR is the handoff point between “I changed something” and “the team is willing to own this change.”

PR summary

Summarize this pull request for a reviewer.

Include:
- business purpose;
- files changed;
- behaviour changed;
- tests run;
- known limitations;
- risks requiring reviewer attention.

Use only information present in the PR.

Review workflow

  1. Open the PR.
  2. Read the generated summary.
  3. Open Files changed.
  4. Select an important diff.
  5. Ask Copilot to explain the change and identify risks.
  6. Review unresolved feedback.
  7. Run tests/CI evidence.
  8. Make the final human review decision.

14. Module-by-Module Learning Guide

Module 1 — Responsible AI

Focus: Understand risks before using AI. Learn the six principles and how to apply them to AI-assisted development.

Takeaway: “Useful” is not enough. AI output must also be responsible, reliable and reviewable.

Module 2 — Introduction to GitHub Copilot

Focus: Understand Copilot, suggestions, interaction modes, setup, plans and troubleshooting.

Takeaway: Know how to move between autocomplete and conversational assistance.

Module 3 — Prompt Engineering

Focus: Learn how clarity, context, constraints and expected output affect Copilot responses.

Takeaway: Better instructions produce more relevant assistance.

Module 4 — Advanced Features

Focus: Chat, Inline Chat, slash commands, agents, project context, testing and documentation.

Takeaway: Combine features instead of using them in isolation.

Module 5 — Across Environments

Focus: IDE, Chat, GitHub.com and command line.

Takeaway: Copilot follows the developer across the workflow.

Module 6 — Management & Customization

Focus: Plans, policies, privacy, exclusions, public-code matching and troubleshooting.

Takeaway: Enterprise AI needs governance as well as productivity.

Module 7 — Developer Use Cases

Focus: Map Copilot to productivity and SDLC activities while understanding limitations.

Takeaway: Measure value by outcomes, not by how much code AI generated.

Module 8 — Unit Testing

Focus: Generate tests, target edge cases, run tests and fix failures.

Takeaway: Generated code becomes useful only after verification.

Module 9 — Copilot Business

Focus: Understand organizational use, access management and business capabilities.

Takeaway: Team adoption requires centralized controls.

Module 10 — Copilot Enterprise

Focus: Enterprise integration, repository context, collaboration, documentation and code review capabilities.

Takeaway: Copilot can become part of organizational development workflows, not just an editor extension.

Module 11 — JavaScript

Focus: Apply Copilot to a JavaScript project using prompts and live suggestions.

Takeaway: The principles transfer directly to a real language/project.

Module 12 — Python

Focus: Apply Copilot to a Python project/API and use live suggestions effectively.

Takeaway: Prompting and context are language-independent skills.

16. Final Challenge — Put It All Together

Give the learner this requirement:

Add a “Clear All KPIs” button.

Constraints:
- keep the existing UI style;
- ask for confirmation before deleting;
- add unit tests;
- update README;
- prepare a PR summary;
- do not break existing functionality.

The learner must choose the workflow

1. Ask/understand → 2. Plan → 3. Implement → 4. Test → 5. Fix if needed → 6. Update docs → 7. Review → 8. PR.

Then ask: “Which Copilot capability did you use at each step, and why?”

17. The One-Minute Mental Model

Don't know → Ask.

Need a decision → Plan.

Need execution → Agent.

Need a focused edit → Inline Chat.

Need a common task → Slash command.

Need terminal help → CLI.

Changed code → Test.

Test failed → Diagnose → Fix → Rerun.

Changed behaviour → Update documentation.

Ready to collaborate → Review → PR.

Always → Provide the right context and verify the result.
